# 家計とカード刷新 Phase 0・1

## 現状

調査対象は `yohaku1228/yohaku1228.github.io` の main（8152263）。ルートの単一HTMLに家計と楽天チェッカーのHTMLを埋め込み、iframeで切り替える。公開ファイルはHTML、アイコン、マニフェスト、README。データは同じオリジンの端末内にあり、GitHubには実データがない。家計は `kakeibo_data_v5`、楽天は `rakuten_alert_checker_v3`。一括バックアップの形式は `finance-unified-v1`。楽天のAPIキー・モデル設定は別の端末内キーで、バックアップ対象外。旧アプリからFirebaseの実運用に必要な接続は確認できない。

家計は月別収支、口座別必要額、振込確認。楽天は速報と本明細の照合、手入力、画像抽出、カード別引落見込み。引落見込みを家計へ転記できる。刷新後は家計の支出と資金決済を共通モデルで扱う。独立した楽天画面とiframeは刷新版から外し、カード別管理、照合、振込確認を段階的に引き継ぐ。

## 移行手順

1. データが入っている端末・起動方法ごとに旧版の「まとめて保存」を実行する。Safariとホーム画面のアプリに別々のデータがある場合は双方で保存する。公開先が旧ドメインの場合も、そのドメインで書き出す。ファイルは個人の保管先に置く。
2. 新アプリの設定で旧バックアップを選び、家計の月数と楽天明細の件数を照合する。Phase 1は検査のみ。旧キーへの書き込みや明細の自動変換は行わない。実データをリポジトリへ登録しない。
3. 新版を使い始める月を決める。過去は旧バックアップで保全する。開始月の予算・固定費は専用の初期設定ファイルを読み込み、開始時点の口座残高と今後の引落予定を照合する。
4. 後続フェーズの変換はプレビューと明示確定を分ける。旧家計のカード行は引落予定候補、楽天の購入は利用記録候補。利用日や支払経路の不明な旧記録は手動確認とし、同じ額という理由で結合しない。元ファイル、件数、合計、変換対象外を照合する。同じ元IDを再取込しても追加しない。
5. 新版の設定でJSONを保存し、検証用環境で復元を試す。復元時は現在のデータも退避する。夫婦同期は、2端末で同時更新・失敗からの再送・世帯間の分離・復元を確認してから共同利用する。

## 構成と選定

- フロントは React、TypeScript、Vite、Tailwind CSS、Lucide、Zustand。現行公開ルートとは別に `refresh/` でレビューする。PWAのインストール範囲も別にする。
- 推奨は Supabase Auth＋Postgres＋RLS＋非公開Storage＋Edge Functions。世帯所属は認証済みユーザーと紐づけ、登録は招待した夫婦2人に限定する。利用者IDをクライアントの申告だけで信用しない。RLSは各行と画像の読み書きの両方で検証する。金額は整数とし、同じ操作IDの再送を一意制約で防ぐ。編集時はリビジョンを比較し、削除を同期できる設計にする。
- Cloudflare Workers＋D1はSQLiteをWorkerから使える。採用する場合は認証プロバイダー、招待、世帯認可、画像保存、差分同期のAPIを別途設計する。2人規模の初期実装ではSupabaseの統合構成が扱いやすい。無料枠の上限と休止・復旧条件は契約前に確認する。サービス契約・接続はPhase 1の対象外。
- AIは認証付きサーバー関数に限定。サーバー側の秘密情報と許可モデルを使う。画像・履歴を送るのは利用者が実行したときだけにし、件数・容量・呼び出し回数を制限する。助言用の金額はアプリで計算し、画像抽出は確認画面を経て保存する。

参考：[Supabase データの保護](https://supabase.com/docs/guides/database/secure-data)・[無料枠](https://supabase.com/docs/guides/platform/billing-on-supabase)・[Cloudflare D1](https://developers.cloudflare.com/d1/)・[D1 料金](https://developers.cloudflare.com/d1/platform/pricing/)

## データと計算

`src/model.ts` が型定義。世帯ごとに口座、メンバー、カテゴリー、月次予算、年次予算、固定費、支払手段、支出、振込を保持する。端末内の保存形式にバージョンを付け、画面から保存先を切り替えられるようにする。Phase 1は端末内のスナップショット。同期時は世帯ID・各行のIDを維持し、クラウドの行単位の更新へ移す。

利用日で生活費を集計し、引落日は資金繰りにだけ使う。口座間移動と実際の貯蓄移動は消費支出から除外する。予算は予定配分、固定費の積立は資産形成、カードの返金は負数の取引。妻の負担が直接支払の場合は家計全体の収入・負担額に残し、口座への給与入金からは除外する。固定費は登録した終了月まで発生する。月次・年間の計画と実績は別々に表示する。

1. Phase 0：現行調査、移行設計、型と画面構成。

3. Phase 2：認証と世帯分離の土台を整え、画像抽出・商品分類・合計と重複の照合を追加する。
4. Phase 3：週間食費の調整、助言と献立、節約チャレンジ。
5. Phase 4：2端末の同期・競合・復元試験、長期分析、PWAと実機の仕上げ。共同利用はこの検証後。
